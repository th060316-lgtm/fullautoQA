title
Finalization: consolidate rollback and offline gates into one real-machine run
body
## Purpose

Move as much of Final technical acceptance as possible onto the real Windows machine in one pass, without returning to blocker-by-blocker local debugging.

### This PR changes the local final-completion route

The existing local runner already performs:
1. preserved donor reconstruction
2. current Source reconstruction + Candidate build
3. bundled Source regression
4. fresh START_QA selftest
5. fresh A→B→A real-game series
6. environment readback

This PR extends it to a seven-stage real-machine finalization route:

1. donor reconstruction
2. Candidate build
3. bundled Source regression
4. fresh START_QA selftest
5. fresh A→B→A
6. **fresh preserved-predecessor rollback qualification**
7. combined local environment/final gate readback

### Real-machine gate behavior

The normal `RUN_LOCAL_COMPLETION.cmd` now passes `-RequireOffline`.

A technical local PASS requires:
- standard non-admin session
- Candidate build/integrity PASS
- bundled Source regression PASS
- fresh Candidate START_QA selftest PASS
- fresh A→B→A PASS with exactly three Result ZIPs
- preserved predecessor restored fresh + START_QA selftest PASS
- persistent user/machine PATH unchanged
- no up non-loopback IP interfaces observed at run start, all three final runs, and run end

Rollback evidence and any rollback RESULT_FOR_CHATGPT.zip readback are preserved before temporary workspace cleanup.

### Important scope limits

- This does **not** claim a complete Registry-write audit; that remains a separate unresolved evidence boundary.
- It does not turn technical A→B→A into Human/Product/Stable PASS.
- GitHub-hosted checks remain preflight. The new local route is intended as the primary technical acceptance evidence.
- Rollback is placed after A→B→A so a rollback failure does not prevent collection of the other final technical evidence in the same machine run.

Issue #1 remains the DoD authority; Issue #25 remains the current completion-route strategy authority.

しかし現状のまま実機に載せても同じ境界で止まる可能性が高い: Assert-RealMachineHandoff は '開発版/transfer/TRANSFER_MANIFEST.json' など同じ非ASCIIリテラルで解決しており、B節の仮説が正しければ preflight は実機で再び TRANSFER_MANIFEST_MISSING を報告する。つまり PR #29 は真の入力状態（ファイルはあるがパスが化けている）を明らかにせず、同じ誤報をより整然と出すだけになる。preflight失敗時に「解決済み絶対パスのbytes」「repo root直下の一次階層listing」を出力しない限り、3回目までの失敗と情報量的に変わらない。

結論: 部分採用 — (a) 失敗時のpath bytes/listing出力を追加、(b) encoding欠陥クラス修正とPS5.1 full-checkout契約テスト（G参照）と同族で統合、(c) parse緑化、の3条件を満たしてから。PR #29は完成経路改善ではなく診断改善である。診断は必要だが、診断だけではIssue #1の残22項は1つも閉じない。
G. Completion-route defects（構造上の欠陥）
CI/実機の責任境界に穴がある（最重要）: 唯一のPS5.1 CIは2ファイルsparse-checkoutで実行されるため、入口パス解決が実ツリー構造に対して検証されない。その結果、実機runが「入口コードの初回実行環境」になっている。これは  Issue #25 が自ら禁じた「user real-machine runを開発ループとして使わない」に、意図せず違反している状態。
欠陥クラスの regression management が存在しない: PR #19が特定・修正した「PS5.1 non-ASCII literal misread」という欠陥クラスを、PR #26が「declared repo-relative path」移行で再導入した。defect-class contract test（Issue #25が宣言したもの）が実際にはこのクラスをカバーしていない。個別の修正は繰り返されているが、修正済み欠陥クラスが再発しない契約が今まで一切の再構成で維持されていない。これが「入口で同じ止まり方を3回」の工程面の根因。
重いjobがPR上で常に skipped: candidate build / final-series はworkflow gate条件によりPR headで走らない。つまり「Candidate buildに影響する変更」は全て、merge後に初めて実証される。PR #27のPhase-3側がそのまま未実行なのはこの構造の帰結。
Management/Sales Gateの証拠生産者が不在: evaluatorは存在するのに、Final series runは常に MANAGEMENT_SIGNAL_ABSENT / SALES_OBSERVATION_INCOMPLETE。Gateを要求的側（Issue #1）に置いたまま、証拠を生産する側（Final runのどこにManagement/Salesの入力を記録させるか）が設計されていない。これはGate過剰ではなくパイプライン断絶。
自己証明の陳腐化がチェックリストに反映されない: C節の通り、superseded Candidateの証拠にanchorしたchecked項がそのまま残る。no-reuse規律は文章としては正しいが、チェックリスト運用に機構化されていない。
観測器の実機実績ゼロ: offline/network観測コンポーネントは実機で一度も正常動作していない（3回とも入口で停止、3回目は観測自体も失敗）。「完全offline PASS」を閉じる装置の実機動作証明が、実機受入より前に必要。

責任分離の要点：
CI = 証明不能な環境差を潰す場所（encoding, PS5.1, path長, entry解決）。実機は検証環境ではなく受入環境。
Candidate freeze = identityの一点凍結。freeze後にSourceが変われば再freezeは明示的决策としてのみ行う。
Evidence = repo外・sealed（PR #26で成立済み、維持）。
Human = 自動Proxyと別の、手順書化された記録収集（30秒/5分評価の採点者・記録形式・session分離を、機械が撮った録画と紐付ける）。Human未実施を自動PASSにしない現行規律はそのまま。
I. One-pass completion sequence
入口境界の封鎖: encoding欠陥クラスの修正（.ps1 のBOM強制 or ASCII-only解決 or PR #19型discoveryの復活）+ PS5.1 full-checkout 契約テスト追加（同commitで Assert-RealMachineHandoff が実ツリーにPASSするまで実機run禁止）。PR #29はここに統合。
PR #27 をmerge（local runner側にも同不変性監査を接続）。Phase-3 candidate build の skipped問題もこの機会に見直し（PR headでも軽量build-path契約を走らせる）。
Management/Salesの証拠生産者をFinal series planに接続し、MANAGEMENT_SIGNAL_ABSENT が出ない run をhostedで1回作る。
OCR決断：最小OCR実装か、Capability NOT_RUN契約の明文化（fake禁止のまま）。
Candidateを一度だけfreeze（Size/SHA-256/ prepared_source_fingerprint 記録）。
hosted preflight全緑 → 実機1回だけ RUN_LOCAL_COMPLETION.cmd（offline・非admin・fresh extraction）。preflight失敗時は証拠bundle解析まで一切コード変更しない。
Human protocol実施（30秒/5分/product test、別session・録画紐付）。
Management/Sales/Product → Stable 判定 → Issue #1 checklist の checked/unchecked を新Candidate証拠に再anchor。
J. Stop conditions
即時停止（既に成立）: 同一実機入口停止が3回。よって「CIで同commitの入口契約が緑になる前の実機run」は今後一切禁止。4回目は根拠なく、必ず同じ結果になる。
preflight失败時に「原因特定に足る新情報（解決済みpath bytes・listing）が出ないpreflight」を再度実機へ送ることを禁止。
freeze後のSource変更を伴う修正を、Issue #1完了前に2回以上行った場合 → それは局所ループの再開なので、route再設計に強制昇格。
実機full runがpreflight後の別stageで2回連続失敗した場合 → stage単位修正ではなくroute単位の分析（Issue #25コメント欄）を必須とする。
MANAGEMENT_SIGNAL_ABSENT が新Candidateの全runで出続けた場合 → Gate側でなく証拠生産側の設計欠陥として扱う。
K. Final recommendation — 次の内部作業を一つに絞る
「実機入口をCIで証明可能にする」一点に絞る: encoding欠陥クラスを修正し、full checkoutした実ツリーに対して Assert-RealMachineHandoff（PR #29のpreflight、失敗時のpath bytes/listing出力を含む）を Windows PowerShell 5.1 で実行するCI契約テストを追加する。これが緑になるまで、実機再走・Candidate再freeze・他Feature作業（OCR等）はすべて後回し。
理由: 3回の入口停止は偶然ではなく、PR #19が既に特定した欠陥クラスの再発（confidence ~0.8）が最も整合する。この境界はCIなら分単位・無料で反復でき、実機なら1回ごとに人的コストとEvidence混乱を生む。ここを閉じない限り、PR #27/#29含むすべての修正はStage 0に到達できず、Issue #1の残22項は1項も動かない。逆に、ここを閉じれば現行6/7-stage設計は host CI → 実機1回 → 3総本山Gate という本来の受入形に戻り、DoD到達は工程上可能である。
